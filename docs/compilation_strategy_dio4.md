# Dio v4 Compilation Strategy: A Summary of Key Concepts

This document summarizes the core academic concepts that underpin the architectural design of Dio v4. The strategy is heavily influenced by research presented in "How to Architect a Query Compiler, Revisited" (Tahboub, Essertel, Rompf, 2018) and "A SQL to C Compiler in 500 Lines of Code" (Rompf, Amin, 2015).

The central idea is to build a **staged query compiler** that leverages **Futamura projections** and a **callback-based execution model** to generate highly efficient, specialized native code.

## 1. The First Futamura Projection: Compilers from Interpreters

The theoretical foundation of our approach is the first Futamura projection, which provides a formal link between interpreters and compilers. It can be stated as:

```
Specializer(Interpreter, Program) = Compiled_Program
```

In our context:
- **Interpreter**: A simple, high-level interpreter for a query language (like relational algebra).
- **Program**: A specific query to be executed (e.g., a SQL query plan).
- **Specializer**: A tool that can partially evaluate the interpreter, given the static query.
- **Compiled_Program**: The output is a new program (native code) that is a specialized version of the interpreter for that one specific query. This resulting program runs much faster because all the interpretive overhead related to parsing and dispatching on the query structure has been removed.

Dio v4 is essentially a practical, programmatic implementation of this principle. We write a query plan interpreter, but we "stage" it. This means we write it in a way that when the interpreter runs, it doesn't compute the result directly but instead generates the native code that will compute the result.

## 2. Staging and Programmatic Specialization

Instead of relying on a fully automatic "specializer" (a complex tool to build), we use **staging**, a technique also known as multi-stage programming. We, as programmers, decide which parts of our interpreter are **static** (known at compile-time) and which are **dynamic** (only known at run-time).

- **Static**: The query plan itself, schema information, operator types (`filter`, `join`, etc.).
- **Dynamic**: The actual data in the columnar arrays.

By representing dynamic values with special types (e.g., `Staged<T>`), we can write an interpreter that executes at compile time. When this interpreter encounters operations on `Staged` values, it doesn't perform them but instead records them as instructions in a target language (Cranelift IR). This process, called **programmatic specialization**, gives us fine-grained control over code generation while allowing us to write the compiler logic in a high-level, straightforward style.

## 3. Push-based (Data-Centric) vs. Pull-based (Volcano) Models

Traditional database systems often use the "Volcano" or iterator model, which is **pull-based**:
- Each operator has a `next()` method.
- The root operator calls `next()` on its child, which calls `next()` on its child, and so on, until a tuple is pulled from the source.
- **Problem**: This model is inefficient for compiled queries. Each `next()` call is a virtual function call, and the logic is spread across many functions, making it hard for the compiler to optimize.

Dio v4 adopts the **push-based** or **data-centric** model, which is far more amenable to compilation:
- Operators are structured as **producers** and **consumers**.
- A producer (e.g., a table scan) generates tuples and "pushes" them to its consumer (e.g., a filter).
- This inverts the control flow, leading to tight loops that process a single tuple through an entire pipeline of operators.

## 4. Callback-Based Compilation

The push-based model is implemented using a **callback-based** (or closure-based) architecture.

- A producer operator takes a consumer (a callback function or closure) as an argument.
- The producer generates its data and, for each tuple, invokes the consumer callback with that tuple.
- The consumer's logic (e.g., applying a filter) is contained within the callback.

This has a powerful effect: the producer's loop and the consumer's logic are naturally **fused** together in the generated code. For a `scan -> filter -> project` pipeline, this results in a single, tight loop:

```c
// Fused code generated by a callback-based compiler
for (int i = 0; i < length; i++) {
    // Scan logic
    int age = age_column[i];
    
    // Filter logic (fused inside the scan loop)
    if (age > 25) {
        // Project logic (fused inside the filter)
        char* name = name_column[i];
        output_column[count++] = name;
    }
}
```

This approach eliminates intermediate data materialization and the overhead of function calls between operators, resulting in code that is significantly more cache-friendly and performant.

By combining these techniques, Dio v4 will transform high-level query plans into specialized, fused, low-level native code, achieving performance competitive with hand-written C code while retaining a high-level, compositional architecture.
